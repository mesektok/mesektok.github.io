### 🎙️ 오늘의 팟캐스트
블로그 빌드가 자꾸 멈춘다면? 이미지 변환 작업의 함정

&nbsp;

### 📌 에피소드 주요 내용
- Jekyll 블로그 빌드가 이미지 변환 작업에서 멈추는 원인은 플러그인의 복잡성과 GitHub Pages의 36분 제한 시간
- 사전 이미지 최적화, 불필요한 플러그인 제거, 로컬 빌드 테스트, 빌드 로그 분석 등 실질적인 해결 방안
- 과도한 자동화보다는 로깅과 모니터링을 통해 병목 지점을 파악하는 것이 근본적인 해결책

### 🎧 전체 대본
**지혜:** 안녕하세요, 여러분! 오늘은 특별한 손님을 모셨어요. Jekyll 블로그를 운영하시면서 빌드 문제로 고민하셨던 노교수님이에요. 교수님, 안녕하세요!

**박교수:** 안녕하네. 은퇴 후 취미로 기술 블로그를 시작했는데, 예상 밖의 문제들을 만났어. 특히 빌드가 자꾸 멈춰서 말이야. 처음엔 마크다운으로 글을 쓰고 커밋하면 자동으로 배포되는 게 정말 신기했는데, 몇 달 뒤부터 이미지 변환 작업에서 빌드가 무한 대기 상태에 빠지는 거야.

**지혜:** 아, 그럼 정말 답답하셨겠네요! 이게 교수님만의 문제는 아니었다고 들었는데, 어떤 상황이었어요?

**박교수:** 맞아. GitHub 이슈 추적 시스템을 보니 수많은 개발자들이 같은 문제를 겪고 있었어. 특히 'Build stuck at running jobs (image transformation)'이라는 이슈가 정확히 내 상황을 설명하고 있었지. 나는 과거 강의 자료와 실습 사진들을 블로그에 올리기 시작했는데, 고해상도 스캔본들이 섞여 있었어.

**지혜:** 아, 그럼 이미지가 많으니까 더 복잡했을 거네요?

**박교수:** 그렇지. jekyll-picture-tag 같은 이미지 최적화 플러그인들이 모든 이미지를 WEBP 포맷으로 변환하고, 여러 해상도의 썸네일을 생성하려다 보니 빌드가 몇 시간을 넘게 소비했어. 그런데 GitHub Pages는 기본적으로 36분 안에 빌드가 완료되어야 한다는 제약이 있거든. 시간이 초과되면 빌드는 실패하고 블로그는 업데이트되지 않아. [지혀] 정말 그 답답함이 느껴져요. 그래서 어떻게 해결하셨어요?

**박교수:** 네 가지 방법을 시도했어. 첫 번째는 사전 최적화야. ImageMagick 같은 도구로 로컬 환경에서 먼저 이미지 크기를 줄이고 포맷을 변환하는 거지. 원본 이미지 크기를 60% 줄이는 것만으로도 빌드 시간을 절반 이상 단축할 수 있었어. 두 번째는 불필요한 플러그인을 제거하는 거야. 모든 자동화가 필요한 건 아니니까 말이야. GitHub Pages가 공식 지원하는 제한된 플러그인만 사용하니 극적으로 빨라졌어.

**지혜:** 와, 그런 단순한 방법으로도 효과가 있었다니! 다른 방법들도 있으셨나요?

**박교수:** 세 번째는 로컬에서 먼저 전체 빌드를 테스트하는 거야. `jekyll build` 명령어로 로컬에서 문제가 없으면 GitHub에 푸시해도 대부분 성공하지. 네 번째는 GitHub Actions의 빌드 로그를 자세히 읽는 거야. 어느 단계에서 시간이 오래 걸리는지 정확히 알 수 있거든. 내 경우 특정 포스트의 이미지들이 병목이었고, 그것만 재처리하니 해결됐어.

**지혜:** 정말 실용적인 팁들이네요! 마지막으로 교수님이 느낀 교훈이 있으신가요?

**박교수:** 자동화는 축복이지만 과도한 자동화는 독이 될 수 있다는 거야. 학계에서 30년을 가르치면서 배운 것 중 하나지. 각 플러그인이 빌드 프로세스에 어떤 영향을 미치는지 이해하고 사용해야 한다는 뜻이야. 문제 해결의 첫 단계는 항상 로깅과 모니터링이다.

**지혜:** 정말 좋은 조언들이에요! 블로그 빌드 문제로 고민하시는 분들이라면 오늘 교수님 팁들이 정말 도움될 것 같아요. 더 자세한 내용은 블로그 원문에서 확인하실 수 있어요. 노교수님, 오늘 말씀해주셔서 감사합니다!

**박교수:** 고마워, 지혜. 혹시 비슷한 문제를 겪는 분들이 계시다면 댓글로 공유해 주길 바라네.
