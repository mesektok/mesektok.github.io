## 시작하며: 나의 좌절했던 첫 경험

저는 대학에서 30년 넘게 컴퓨터공학을 가르쳐왔습니다. 작년 67세의 나이에 개인 블로그를 시작하기로 결심했을 때, 저는 이 일이 이렇게 어려울 줄은 몰랐습니다. GitHub Pages에 Jekyll 블로그를 올리겠다는 야심 찬 계획은 첫 주부터 무너졌습니다. 로컬에서는 완벽하게 보이는 블로그가 GitHub에 푸시하는 순간 build failed 메시지와 함께 사라져버렸거든요.

처음엔 GitHub의 자동 빌드 시스템 때문이라고만 생각했습니다. 하지만 며칠간의 고민과 오류 로그 분석 끝에 깨달았습니다. **로컬 환경과 GitHub Pages의 빌드 환경이 일치하지 않았던 것**이 핵심 문제였습니다. 이제 저는 이 문제를 완전히 해결했고, 그 경험을 나누고 싶습니다.

## GitHub Pages와 로컬 Jekyll 환경의 불일치 문제

많은 초보자들이 간과하는 부분이 바로 이것입니다. 당신의 컴퓨터에서 설치한 Ruby, Jekyll, Bundler의 버전이 GitHub Pages의 빌드 환경과 정확히 일치해야 한다는 점입니다.

저는 처음에 그냥 `gem install jekyll`로 최신 버전을 설치했습니다. 그 결과 Ruby 3.2.0과 Jekyll 4.3.2가 설치되었죠. 그런데 GitHub Pages는 다른 버전 조합으로 빌드를 시도했던 것입니다. 마치 다른 언어로 된 책을 번역하려는 것처럼 호환성 문제가 발생했던 겁니다.

해결책은 간단했습니다. **Gemfile을 사용하여 의존성을 명확히 정의**하는 것이었습니다. Jekyll Chirpy 테마를 사용한다면, `Gemfile`에 정확한 gem 버전들을 명시해야 합니다. 특히 `github-pages` gem을 Gemfile에 포함시키면, GitHub Pages와 동일한 버전의 모든 의존성이 자동으로 설치됩니다.

```ruby
gem "github-pages", "~> 228", group: :jekyll_plugins
```

이 한 줄이 제 모든 빌드 실패 문제를 해결했습니다. 그 후 `bundle install`을 실행하고, 항상 `bundle exec jekyll serve`로 로컬 서버를 실행했을 때, 로컬과 GitHub Pages의 결과가 완벽하게 일치했습니다.

## Bundler를 활용한 정확한 환경 재현

저는 45년을 개발자로 살아오면서 "환경"의 중요성을 수없이 목격했습니다. 하지만 이제는 그 교훈을 다시 한 번 명확히 깨달았습니다.

Bundler는 Ruby 프로젝트의 의존성 관리 도구입니다. 단순히 gem을 설치하는 것만이 아니라, 정확한 버전들을 기록하고 어떤 환경에서든 동일한 결과를 보장합니다. 이것은 소프트웨어 공학에서 말하는 "재현 가능성(Reproducibility)"을 확보하는 것과 같습니다.

제가 처음 실수한 부분은 `Gemfile.lock` 파일을 무시했다는 것입니다. 이 파일은 자동으로 생성되지만, 무언가 "자동 생성 파일"이라고 생각해 GitHub에 커밋하지 않았습니다. 큰 실수였습니다. `Gemfile.lock`을 반드시 저장소에 포함시켜야 합니다. 이 파일이 있어야 GitHub Actions가 정확히 같은 버전으로 빌드할 수 있기 때문입니다.

제 권장사항은 이렇습니다:

1. 프로젝트 루트에 `Gemfile` 생성
2. `bundle install` 실행 (자동으로 `Gemfile.lock` 생성)
3. `Gemfile`과 `Gemfile.lock` 모두 GitHub에 커밋
4. 항상 `bundle exec jekyll serve`로 로컬 테스트
5. 변경사항이 있을 때마다 `bundle update` 실행 후 재테스트

이 과정을 따르면 95% 이상의 빌드 실패를 예방할 수 있습니다.

```bash
bundle exec jekyll serve --incremental
```
