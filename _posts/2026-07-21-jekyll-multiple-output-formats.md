## 은퇴 후 블로그를 시작했던 이유

지난 2년간 저는 40년을 근무한 대학을 떠나고 개인 블로그를 시작했습니다. 컴퓨터과학을 가르쳤던 경험이 아까워서 학생들과의 지식 공유를 계속하고 싶었거든요. Jekyll을 선택한 것은 여러 이유가 있었지만, 역시 마크다운 기반의 단순함과 GitHub Pages의 무료 호스팅이 가장 큰 매력이었습니다.

처음엔 일반적인 블로그 포스팅만 했습니다. 강의 자료, 연구 노트, 학생 질문에 대한 답변들을 올렸죠. 그런데 문제가 생겼습니다. 제 블로그를 찾는 사람들이 점점 늘어나면서, 이번엔 강의 일정 정보를 달력에 자동으로 추가할 수 있으면 좋겠다는 요청이 들어온 것입니다. HTML 페이지도 필요하고, 동시에 iCal 형식의 캘린더 파일도 필요하다는 뜻이었습니다.

## Jekyll의 한계와 첫 번째 좌절

처음엔 너무 간단할 거라고 생각했습니다. 마크다운 파일 하나에서 HTML과 iCal 파일을 동시에 생성하면 되지 않을까 하는 순진한 생각 말입니다. 하지만 Jekyll의 문서를 뒤져봐도 답이 없었습니다.

Jekyll의 기본 구조는 하나의 레이아웃 파일이 하나의 출력 형식만 생성하도록 설계되어 있었거든요. `_layouts` 폴더의 `default.html`은 HTML을 만들고, 그걸로 끝이었습니다. 같은 콘텐츠로 다른 형식의 파일을 만들려면? 완전히 다른 접근이 필요했습니다.

GitHub의 공식 Jekyll 이슈 페이지에서 이와 동일한 질문을 발견했을 때 정말 안도했습니다. 저 혼자만의 문제가 아니었던 것이죠. 많은 개발자들과 콘텐츠 크리에이터들이 같은 고민을 하고 있었고, 결국 이것은 Jekyll의 설계상 근본적인 제한이었습니다.

## 실전 해결책: 플러그인과 후처리

다행히 문제를 푸는 방법들이 있었습니다. 완벽하지는 않지만, 실무에서 충분히 작동하는 솔루션들 말입니다.

**첫 번째 방법은 Jekyll 플러그인을 직접 만드는 것**입니다. Ruby 스크립트를 작성하여 빌드 과정에서 HTML과 동시에 iCal 파일을 생성하는 겁니다. 저는 `_plugins` 폴더에 `ical_generator.rb` 파일을 만들어서, 각 포스트의 front matter에서 날짜와 설명 정보를 읽어 iCal 형식으로 변환했습니다. 이 방법은 가장 깔끔했고, 자동화도 완벽했습니다.

**두 번째 방법은 GitHub Actions를 활용하는 것**입니다. Jekyll 빌드가 완료된 후, 별도의 스크립트로 필요한 형식들을 추가로 생성하는 워크플로우를 구성했습니다. Python이나 Node.js를 써서 `_site` 폴더의 HTML 파일들을 읽고, 필요한 메타데이터를 추출한 뒤 PDF나 iCal 파일로 변환하는 방식입니다. 이것도 꽤 효율적이었습니다.

**세 번째는 좀 더 실용적인 방법**으로, 여러 개의 포스트 파일을 만드는 것입니다. 같은 내용이지만 서로 다른 레이아웃을 가진 파일들 말이죠. `my-lecture.html`과 `my-lecture.ics` 처럼 말입니다. 조금 중복되지만, Jekyll 플러그인을 배우기 어려운 초보자들에게는 충분히 실용적인 방법입니다.

## 제 블로그에서 실현한 방식

결국 저는 첫 번째 방법을 택했습니다. Ruby 플러그인을 배우는 데 시간이 걸렸지만, 한 번 만들어 놓으니 모든 새 포스트에서 자동으로 작동했거든요. 강의 공지사항을 쓸 때마다 자동으로 iCal 파일이 생성되고, 학생들은 자신의 캘린더 앱에 구독 링크를 추가해서 항상 최신 정보를 받을 수 있게 된 것입니다.

이제 제 블로그는 단순한 블로그를 넘어, 실질적인 정보 배포 시스템이 되었습니다. 같은 마크다운 파일 하나에서 웹 페이지, 캘린더 파일, 나중엔 RSS 피드까지 여러 형식으로 자동 생성됩니다. 이것이 정적 사이트 생성기의 진정한 힘이라고 생각합니다.

혹시 당신도 Jekyll 블로그를 운영하면서 이런 고민을 하고 있다면, 댓글로 공유해 주세요. 여러분의 구체적인 사용 사례가 다른 독자분들에게도 큰 도움이 될 것 같습니다.
