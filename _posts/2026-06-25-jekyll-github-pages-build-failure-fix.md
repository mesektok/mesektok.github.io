정년을 맞이한 지 3년째, 나는 은퇴 후의 시간을 의미 있게 보내기 위해 GitHub Pages로 기술 블로그를 시작했습니다. 처음에는 간단하다고 생각했는데, Jekyll과 GitHub Pages의 조합은 생각보다 까다로운 함정들이 있었습니다. 특히 로컬에서는 완벽하게 작동하는데 GitHub에 푸시하면 갑자기 빌드가 실패하는 현상은 정말 답답했습니다. 그러나 지난 3년간의 시행착오를 통해 이 문제들을 해결하는 체계적인 방법을 터득했고, 오늘은 그 경험을 여러분과 나누고자 합니다.

## GitHub Pages 빌드 에러 알림을 제대로 이해하기

처음 GitHub Pages 빌드 실패를 경험했을 때, 나는 GitHub에서 보내는 이메일 알림을 무시했습니다. 마치 대학 시절 학생들의 이메일을 곧바로 휴지통으로 보내던 습관처럼 말입니다. 하지만 이것이 첫 번째 실수였습니다. GitHub는 실제로 아주 유용한 오류 정보를 제공하고 있었거든요.

GitHub 저장소의 Settings 탭에 가면 'Pages' 섹션이 있습니다. 여기서 "Build and deployment" 부분을 살펴보면 최근 배포 상태와 실패 로그를 확인할 수 있습니다. 나중에는 GitHub Actions 탭에서 더 자세한 로그를 볼 수 있다는 것도 배웠습니다. 로그를 읽어보니 내가 놓친 부분들이 명확히 드러났습니다. 예를 들어, Ruby 버전 호환성 문제, Gem 의존성 충돌, 또는 마크다운 문법 오류 등이었죠.

내 조언은 간단합니다. 빌드가 실패하면 일단 GitHub에서 제공하는 오류 메시지를 꼼꼼히 읽으세요. "The page build failed"라는 일반적인 메시지 아래에는 항상 구체적인 원인이 숨어 있습니다. 이 메시지들이 문제 해결의 70%를 차지한다고 해도 과언이 아닙니다.

## Gemfile과 의존성 관리: 로컬과 서버의 동기화

2년 전, 나는 Chirpy 테마를 적용하면서 큰 문제를 마주했습니다. 로컬 개발 환경에서는 `bundle exec jekyll serve`로 완벽하게 작동하는데, GitHub에 푸시하면 항상 빌드가 실패하는 것이었습니다. 대학에서 30년간 전자공학을 가르치며 경험한 것이라면, 이런 문제는 거의 항상 환경의 불일치에서 비롯된다는 점입니다.

문제의 원인은 Gemfile.lock 파일이었습니다. GitHub Pages는 특정 버전의 Jekyll과 플러그인만을 지원하며, 내 로컬 환경과 GitHub의 서버 환경이 다른 버전을 사용하고 있었던 것입니다. 예를 들어, 내 MacBook에는 Ruby 3.2가 설치되어 있었지만, GitHub Pages는 Ruby 2.7을 지원했습니다.

해결책은 두 가지였습니다. 첫째, Gemfile에 `github-pages` gem을 명시적으로 추가하고, 로컬에서도 동일한 버전을 사용하도록 Gemfile.lock을 유지하는 것입니다. 둘째, GitHub Actions를 통해 커스텀 빌드 프로세스를 정의하는 것입니다. 나는 후자를 선택했습니다. `.github/workflows/jekyll.yml` 파일을 생성하여 빌드 과정을 명시적으로 제어하기 시작했고, 이후로는 빌드 실패가 거의 사라졌습니다.

## 마크다운 문법과 Front Matter 검증의 중요성

은퇴한 지 얼마 후, 나는 마크다운 문법의 중요성을 깨달았습니다. 특히 Jekyll의 Front Matter 부분에서 YAML 형식을 잘못 사용하면 전체 빌드가 실패합니다. 나는 많은 포스트에서 제목이나 태그에 콜론(:)이나 따옴표를 제대로 이스케이프하지 않아 문제를 겪었습니다.

예를 들어, 제목이 "GitHub: 버전 관리의 모든 것"이라면, Front Matter에서는 `title: "GitHub: 버전 관리의 모든 것"`처럼 큰따옴표로 감싸야 합니다. 또한 tags 배열에서 하이픈(-)이 포함되면 `tags: [GitHub, "Jekyll-Blog"]` 형식으로 하이픈이 포함된 항목만 따옴표로 묶어야 합니다. 이런 세세한 부분들이 빌드 실패의 원인이 되기도 합니다.

나는 이제 매 포스트를 작성한 후 YAML 유효성 검사 도구를 온라인에서 실행해봅니다. 또한 로컬에서 `jekyll build` 명령을 실행하여 에러가 없는지 확인합니다. 이 작은 습관이 GitHub에 푸시하기 전에 90%의 문제를 사전에 방지해줍니다.

정년 후 블로깅을 시작한 지 3년, 나는 이제 거의 모든 상황에서 빌드 실패를 예방하고 해결할 수 있게 되었습니다. 이 경험들이 여러분의 Jekyll 블로그 운영에도 도움이 되기를 바랍니다. 혹시 비슷한 문제를 겪고 계신다면, 위의 방법들을 차근차근 따라 해보세요. 그리고 해결되셨다면, 댓글로 여러분의 경험도 공유해 주시면 좋겠습니다.
