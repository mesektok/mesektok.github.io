### 📌 에피소드 주요 내용
- Jekyll 블로그 빌드 시 이미지 변환 작업에서 발생하는 병목 현상 진단
- 불필요한 플러그인 제거, 로컬 최적화, 캐싱 전략 등을 통한 단계별 해결
- 빌드 시간을 45분에서 3분으로 단축하고 시스템 안정성 확보

### 🎧 전체 대본
**지혜:** 안녕하세요! 오늘은 Jekyll 블로그를 운영하시는 분들이라면 공감할 만한 주제를 가지고 왔어요. 노교수님, 안녕하세요!

**박교수:** 안녕하네. 오늘은 흥미로운 기술 주제를 준비해주었군. Jekyll 블로그의 빌드 문제에 대해 얘기해보자는 것 같은데, 이것은 단순한 기술 이슈를 넘어서 시스템 설계의 근본적인 문제를 드러내는 사례라고 할 수 있네.

**지혜:** 정확히요! 교수님, 간단히 설명해주시면, Jekyll 블로그를 운영하다 보면 빌드 프로세스가 자꾸 멈추는 경험을 하는 사람들이 있다고 하더라고요. 이게 뭐 때문에 발생하는 건가요?

**박교수:** 그것이 바로 이미지 변환 작업에서 비롯된 문제라네. 생각해보면, 블로그에 포스팅이 200개를 넘어가고 각 포스팅마다 3~5장의 고해상도 이미지가 들어가면, 빌드할 때마다 그 이미지들을 여러 형식으로 변환해야 한다는 말이지. 웹피(WebP), AVIF 같은 현대적 형식으로 말이야. 더구나 여러 플러그인이 동시에 같은 이미지를 중복으로 처리하고 있었다면 자연스럽게 병목 현상이 생기게 되는 것이네.

**지혜:** 아, 그러니까 하나의 이미지가 여러 번 처리되는 거군요? 얼마나 심했어요?

**박교수:** 포스팅 하나당 원본을 포함해 최대 24개의 변환된 이미지 파일이 생성되었다고 하네. 이런 작업이 매 빌드마다 반복되면, 결국 GitHub Actions의 컨테이너 환경에서 메모리 부족 현상까지 발생하게 되는 것이다. 로컬 환경과는 달리 CI/CD 환경은 리소스가 제한되어 있거든.

**지혜:** 와, 정말 심각하네요. 그럼 이 문제를 어떻게 해결했어요?

**박교수:** 해결책은 여러 단계로 나뉘는데, 먼저 불필요한 플러그인을 정리하고 로컬에서만 최적화를 진행한 후 CI/CD에서는 이미 최적화된 이미지만 배포하도록 전환했다네. 두 번째로는 이미지 크기를 사전에 정규화했고, GitHub Actions 캐싱 전략을 추가했으며, 마지막으로 빌드 시간을 모니터링하는 플러그인까지 도입했다고 하네.

**지혜:** 결과가 어떻게 되었어요? 빌드 시간이 많이 단축됐나요?

**박교수:** 그것이 놀라운 부분이네. 무려 45분에서 3분으로 단축되었다고 하네. 15배 이상의 개선이다. 더 중요한 것은 이제 빌드가 중간에 멈추지 않는다는 점이야. 이것은 단순한 성능 향상을 넘어 시스템 안정성을 확보한 것이지.

**지혜:** 정말 극적인 개선이네요! 교수님, 혹시 이 글을 보고 계신 분들이 자신의 상황과 비교해보고 싶으시면 어디서 더 자세한 내용을 확인할 수 있을까요?

**박교수:** 당연하지. 더 자세한 기술적 설정 방법과 구체적인 코드 예시는 원문 블로그에 모두 담겨 있네. 자신의 상황에 맞춰 적용해볼 수 있도록 말이야.

**지혜:** 네, 더 자세한 내용은 블로그 원문에서 확인하실 수 있어요. 오늘은 좋은 인사이트 감사합니다, 노교수님!

**박교수:** 반갑네.
