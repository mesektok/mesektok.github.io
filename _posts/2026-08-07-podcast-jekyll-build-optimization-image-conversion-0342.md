- 로컬 최적화, 이미지 규격화, GitHub Actions 캐싱 전략 등 단계별 해결책 적용

### 🎧 전체 대본
**지혜:** 안녕하세요, 여러분! 오늘 저희는 Jekyll 블로그 빌드 문제에 대해 얘기해볼 건데요. 노교수님, 개인 블로그를 운영하시면서 빌드가 자꾸 멈추는 경험을 하셨다고요?

**박교수:** 그렇습니다. 지난 몇 년간 GitHub Pages와 Jekyll로 블로그를 관리해오면서 정말 답답한 경험을 했어요. 포스팅 수가 늘어나고 이미지가 많아지다 보니, 어느 순간부터 빌드 프로세스가 자꾸 멈추기 시작했거든요. 처음엔 GitHub의 서버 문제라고만 생각했는데, 알고 보니 이미지 변환 작업에서 엄청난 리소스를 소비하고 있었던 겁니다.

**지혜:** 오! 그럼 정확히 어떤 증상부터 나타났어요?

**박교수:** GitHub Actions의 대시보드에서는 'Running Jobs' 상태로 계속 진행 중이라고 표시되는데, 실제로는 이미지 변환 작업에서 CPU와 메모리를 극도로 소비하고 있었던 거죠. 새로운 이미지가 많은 포스팅을 올릴 때마다 빌드 시간이 30분을 넘어갔고, 결국 6시간의 타임아웃에 도달하는 악순환이 반복됐습니다.

**지혜:** 와, 그것도 문제네요. 그럼 원인이 뭐였어요?

**박교수:** 문제의 핵심은 제가 여러 개의 이미지 최적화 플러그인들을 동시에 활성화해두고 있었다는 점입니다. jekyll-image-optim, jekyll-picture-tag, jekyll-responsive-images 같은 플러그인들이 같은 이미지를 WebP, AVIF 등 다양한 형식으로 변환하고, 여러 해상도의 썸네일을 생성하면서 연산량이 기하급수적으로 증가했던 거예요. 제 경우 이미지 하나당 원본 포함 최대 24개의 변환된 파일이 생성되고 있었습니다.

**지혜:** 24개요? 그건 정말 많네요. 그럼 교수님은 어떻게 해결하셨어요?

**박교수:** 여러 단계의 최적화를 진행했습니다. 먼저 불필요한 플러그인을 제거하고, 로컬에서만 이미지 최적화를 하고 배포는 이미 최적화된 이미지를 사용하도록 바꿨어요. 두 번째로는 모든 이미지를 600x400에서 2000x1500 사이의 규격으로 정규화했습니다. 그리고 GitHub Actions에서 캐싱 전략을 추가해 이전 빌드의 캐시를 재사용하도록 했어요. 마지막으로 빌드 모니터링 플러그인을 도입했습니다.

**지혜:** 그 결과가 정말 대단했대요. 45분에서 3분으로 단축되셨다고?

**박교수:** 네, 정말 극적인 변화였습니다. 무엇보다 빌드가 중간에 멈추는 현상이 완전히 사라졌어요. 비슷한 고민을 하고 계신 분들이라면, 먼저 어느 플러그인이 가장 시간을 소비하는지 파악하는 것부터 시작하시길 권장합니다. 그것이 첫 번째 진단 단계가 될 테니까요.

**지혜:** 정말 실용적인 조언들이네요! 더 자세한 내용은 블로그 원문에서 확인하실 수 있어요. 노교수님, 오늘 정말 감사합니다!

**박교수:** 감사합니다. 청취해주신 분들께도 도움이 되길 바랍니다.
