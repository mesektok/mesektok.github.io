## 서론: 은퇴 전 마지막 프로젝트에서의 깨달음

저는 소프트웨어 개발 분야에서 20년 이상을 일해온 개발자입니다. 은퇴를 앞두고 개인 기술 블로그를 만들어보자는 생각으로 GitHub Pages와 Jekyll을 시작했는데, 정말 황당한 경험을 하게 되었습니다. 수십 년간 다양한 프로그래밍 언어와 프레임워크를 다루어온 경험이 있었음에도 불구하고, 단순한 블로그 설정에서 여러 번 실패했던 것입니다. 이 과정에서 저는 많은 개발자들이 쉽게 빠질 수 있는 함정들을 발견했고, 그 교훈을 여러분과 나누고자 합니다.

## 내가 직접 경험한 빌드 실패의 원인들

제가 가장 먼저 마주친 문제는 로컬 환경과 GitHub Pages 서버의 Ruby 버전 차이였습니다. 제 노트북에는 Ruby 3.2가 설치되어 있었지만, GitHub Pages에서 사용하는 기본 Ruby 버전은 2.7대였던 것입니다. 이로 인해 로컬에서는 완벽하게 작동하는 사이트가 GitHub에서는 자꾸만 빌드에 실패했습니다. 처음에는 단순한 마크다운 문법 오류라고 생각했는데, Actions 탭의 빌드 로그를 자세히 살펴본 후에야 진실을 알게 되었습니다.

두 번째 문제는 `_config.yml` 파일의 인코딩 문제였습니다. 제가 Windows에서 파일을 수정했을 때 BOM(Byte Order Mark)이 포함된 UTF-8로 저장되어 버렸던 것입니다. 이 작은 바이트들이 YAML 파서를 혼란스럽게 했고, 결과적으로 Jekyll이 설정 파일을 제대로 읽지 못했습니다. 고교 시절 BASIC 언어를 배운 제 경험으로도 설명하기 어려울 정도로 미묘한 오류였습니다.

세 번째는 플러그인 호환성 문제였습니다. 저는 멋진 추가 기능들을 사용하고 싶어서 여러 개의 Jekyll 플러그인을 설치했는데, GitHub Pages의 안전 모드에서는 일부 플러그인만 허용된다는 사실을 뒤늦게 알았습니다. 공식적으로 허용되지 않은 플러그인은 로컬 빌드에서는 작동하지만, GitHub Pages에서는 자동으로 비활성화되어 버렸던 것입니다.

## 해결책과 예방 전략

가장 효과적인 해결책은 GitHub Actions의 빌드 로그를 꼼꼼히 읽는 것입니다. 저는 처음에 에러 메시지를 대충 훑었는데, 나중에 차근차근 읽어보니 정확한 문제가 무엇인지 명확하게 드러났습니다. "The page build failed" 메시지 아래에는 항상 구체적인 원인이 숨어있습니다.

로컬 환경을 GitHub Pages와 동일하게 맞추기 위해, 저는 `Gemfile`에 `github-pages` gem을 명시적으로 추가했습니다. 이렇게 하면 로컬에서 테스트할 때 서버와 동일한 Ruby 버전과 플러그인을 사용하게 됩니다. `bundle install`과 `bundle exec jekyll serve` 명령어로 로컬에서 실제 배포 환경과 동일하게 테스트할 수 있다는 점이 정말 중요합니다.

파일 인코딩 문제를 방지하기 위해서는 `.editorconfig` 파일을 프로젝트 루트에 만들어 모든 개발자가 동일한 인코딩 설정을 사용하도록 강제할 수 있습니다. 그리고 텍스트 에디터(특히 VS Code)에서 파일 저장 시 "UTF-8 without BOM" 옵션을 명시적으로 선택하는 습관도 중요합니다.

플러그인 사용 시에는 [GitHub Pages 공식 문서](https://pages.github.com/versions/)에서 허용된 플러그인 목록을 먼저 확인하고 시작하는 것이 현명합니다. 저는 처음부터 이 목록을 참고했다면 많은 시간을 낭비하지 않았을 것 같습니다.

## 결론: 경험이 모든 것은 아니라는 깨달음

20년의 개발 경력에도 불구하고, 새로운 기술 스택을 배울 때는 항상 겸손해야 한다는 것을 깨달았습니다. GitHub Pages와 Jekyll은 겉보기에 단순하지만, 실제로는 많은 세부 사항들이 숨어있는 시스템입니다. 저 같은 경험 많은 개발자도 이러한 함정에 빠질 수 있으니, 처음 시작하는 여러분은 제 실수를 반복하지 마시기 바랍니다.

지금 바로 여러분의 GitHub Pages 블로그 설정을 점검해보고, 혹시 비슷한 문제를 겪고 있다면 이 글의 해결책들을 차례대로 시도해보세요.
