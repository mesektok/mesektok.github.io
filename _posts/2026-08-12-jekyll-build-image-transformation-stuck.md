## 은퇴 후 취미로 시작한 기술 블로그의 악몽

올해 교수 생활을 마치고 한 달쯤 뒤, 저는 평생 연구한 내용과 학생들에게 전해주던 지식을 정리하려고 GitHub Pages에 Jekyll 블로그를 세웠습니다. 처음엔 마크다운으로 글을 쓰는 것도, Git으로 배포하는 것도 즐거웠죠. 하지만 두 달째 접어들 무렵, 예상치 못한 문제가 터져 나왔습니다.

블로그에 사진을 올릴 때마다 빌드 작업이 중간에 멈춰버린 것입니다. 깃허브 액션 로그를 보면 "running jobs"라는 메시지에서 계속 돌다가 시간초과로 실패했습니다. 처음엔 인터넷 속도 때문이라 생각했지만, 같은 글을 여러 번 업로드해도 같은 현상이 반복되었습니다. 

자료를 찾아보니 이것이 생각보다 많은 Jekyll 사용자들이 겪는 문제였습니다. 특히 GitHub의 공식 이슈 추적 시스템에서도 논의되고 있던 버그였던 것입니다.

## 범인은 이미지 변환 작업이었다

원인을 파악하기 위해 빌드 로그를 자세히 살펴봤습니다. 문제는 Jekyll의 이미지 최적화 플러그인에 있었습니다. 블로그에 업로드한 이미지를 자동으로 여러 해상도로 변환하는 작업이 시작되긴 하는데, 특정 상황에서 무한 루프에 빠져버리는 것입니다.

특히 다음과 같은 경우에 자주 발생했습니다:

**첫째, 큰 용량의 원본 이미지 파일:** 저는 연구 자료로 사용했던 고해상도 사진들(5MB 이상)을 그대로 업로드했습니다. 이 파일들을 처리하려니 변환 작업이 자꾸 중단되었습니다.

**둘째, 동시에 여러 이미지를 올리는 경우:** 한 포스팅에 10장 이상의 사진을 한 번에 커밋하면 변환 큐가 꼬여서 완료되지 않았습니다.

**셋째, 특정 이미지 포맷의 조합:** PNG와 JPG, WebP 등 여러 형식을 섞어서 올렸을 때 더 자주 발생했습니다.

GitHub의 공식 이슈에 따르면, 이 문제는 `jekyll-image-size`나 유사한 이미지 처리 플러그인에서 발생하는 알려진 버그였습니다. 플러그인이 이미지 변환을 큐에 추가했다가 처리 상태를 제대로 업데이트하지 못해 같은 작업을 반복하는 악순환에 빠지는 것입니다.

## 실제로 작동한 3가지 해결책

**첫 번째 해결책: 이미지 사전 처리하기**

저는 업로드 전에 이미지를 직접 최적화하기로 결정했습니다. macOS의 기본 이미지 처리 도구나 무료 온라인 도구(TinyPNG, Squoosh)를 사용해 이미지를 1MB 이하로 압축한 후 업로드했습니다. 이렇게 하자 빌드 시간이 3분에서 30초로 단축되었습니다.

**두 번째 해결책: jekyll-image-size 플러그인 제거**

`_config.yml` 파일에서 이미지 변환 관련 플러그인을 비활성화했습니다. 대신 CloudFlare나 Imgix 같은 외부 CDN 서비스로 이미지 최적화를 넘겼습니다. 이것이 가장 안정적이었습니다.

**세 번째 해결책: 이미지 업로드를 분산하기**

한 번에 모든 이미지를 올리지 않고, 포스팅당 최대 3장씩만 한 번에 커밋하는 방식으로 바꿨습니다. 이렇게 하면 각 빌드 작업이 가볍게 유지되어 문제가 거의 발생하지 않습니다.

## 앞으로의 전략

이제 저는 GitHub Pages로 블로그를 운영할 때 다음 원칙을 지키고 있습니다.

이미지는 항상 사전에 최적화하고, 플러그인의 자동 변환 기능에 의존하지 않습니다. 대신 HTML의 `<img>` 태그나 마크다운에서 명시적으로 이미지 크기를 지정하고, 반응형 이미지가 필요하면 HTML의 `srcset` 속성을 직접 작성합니다.

블로그 운영이 즐거워지자 포스팅 빈도도 높아졌습니다. 빌드 오류로 인한 스트레스가 없어지니 글 쓰는 데만 집중할 수 있게 되었습니다.

혹시 당신도 Jekyll 블로그를 운영하면서 비슷한 빌드 오류를 경험하고 있다면, 이 글의 해결책들을 순서대로 시도해보세요. 특히 이미지 사전 처리가 가장 간단하면서도 효과적입니다.
