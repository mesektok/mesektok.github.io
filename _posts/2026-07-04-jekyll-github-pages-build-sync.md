은퇴 후 블로그를 시작하면서 GitHub Pages와 Jekyll의 매력에 빠졌습니다. 처음에는 그저 마크다운으로 글을 작성하고 푸시하면 자동으로 배포되는 것에 감탄했는데, 한두 달이 지나자 예상 밖의 빌드 오류들이 시작되었습니다. 원격 저장소에는 성공 알림이 왔으나 정작 웹사이트에는 이전 글만 표시되거나, 스타일이 깨져 나타나는 악몽 같은 상황들 말입니다.

그 과정에서 깨달은 가장 중요한 교훈이 있습니다. 바로 로컬 개발 환경과 GitHub Pages의 빌드 환경을 완벽하게 동기화하는 것이 얼마나 중요한지 하는 점입니다. 지난 2년간 겪었던 시행착오를 정리하여 여러분과 공유하겠습니다.

## 로컬 환경 설정이 해결책의 80%

많은 초보자들이 GitHub에 직접 푸시한 후 배포 결과를 확인하는 방식을 취합니다. 저도 처음에는 그랬습니다. 하지만 이는 마치 비행기 승객이 조종실에 들어가 수정 사항을 적용하려는 것과 같습니다. 비효율적일 뿐만 아니라 위험합니다.

로컬 머신에 Ruby와 Jekyll을 정확히 설치하는 것이 첫 번째 단계입니다. Ruby 버전이 중요한데, GitHub Pages가 지원하는 버전과 맞아야 합니다. 저는 처음에 최신 Ruby 3.2를 설치했다가, GitHub Pages가 3.1대를 권장한다는 것을 뒤늦게 알았습니다. 이로 인해 Gemfile의 번들 설정이 자꾸 꼬였습니다.

`bundle install`과 `bundle exec jekyll serve`를 통해 로컬에서 먼저 완전히 같은 환경을 구현해야 합니다. 이렇게 하면 푸시 전에 모든 오류를 발견할 수 있습니다. 제 경험상 이 과정만 제대로 해도 GitHub Pages 빌드 실패의 80% 이상을 사전에 방지할 수 있습니다.

## Gemfile과 Gemfile.lock의 신비로운 역할

처음 몇 개월간 저는 Gemfile을 대충 무시했습니다. 단순히 의존성 목록일 뿐이라고 생각했기 때문입니다. 얼마나 큰 오해였는지 모릅니다.

Gemfile은 프로젝트의 청사진이고, Gemfile.lock은 그 청사진대로 지은 건물의 정확한 도면입니다. 로컬에서 `bundle install`을 실행하면 Gemfile.lock이 생성되는데, 이것이 GitHub Actions 워크플로우에서 정확하게 같은 gem 버전들을 설치하도록 보장합니다.

저는 한 번 실수로 로컬에서 Gemfile.lock을 삭제했다가 다시 생성했는데, 그 후로는 깨끗하게 배포되었습니다. GitHub Pages가 읽는 것은 이 lock 파일이기 때문입니다.

특히 중요한 것은 `github-pages` gem입니다. 이것을 Gemfile에 명시하면 GitHub Pages의 정식 빌드 환경과 동일한 gem 세트가 설치됩니다. 저는 처음에 Jekyll만 설치했다가 나중에 `github-pages` gem으로 변경했고, 그 순간부터 로컬과 원격의 차이가 거의 없어졌습니다.

## 테마 호환성 검증이 시간 낭비를 막는다

Chirpy 테마는 훌륭하지만, 모든 플러그인과 설정이 GitHub Pages의 안전 모드(Safe Mode)와 호환되지는 않습니다. 저는 처음에 이를 몰라서 어떤 플러그인이 문제인지 파악하려고 한 주일을 낭비했습니다.

로컬에서 `JEKYLL_ENV=production bundle exec jekyll build`로 빌드하면 GitHub Pages와 정확히 같은 조건에서 테스트할 수 있습니다. 프로덕션 환경에서만 나타나는 오류들을 미리 잡을 수 있다는 뜻입니다.

제 조언은 새로운 플러그인이나 설정을 적용할 때마다 반드시 로컬 프로덕션 빌드로 검증하라는 것입니다. 5분의 로컬 테스트가 나중에 30분의 디버깅을 절약해줍니다.

지난 2년간 이러한 방식을 고수하면서 저는 단 한 번의 배포 실패도 경험하지 않았습니다. 블로그는 제 업무 시간이나 글쓰기 중단 없이 항상 안정적으로 작동합니다. 여러분도 오늘부터 로컬 환경을 정확히 설정하고 로컬에서 완벽하게 테스트한 후 푸시하는 습관을 들여보세요. 그것이 GitHub Pages와 Jekyll로 장기간 안정적인 블로그를 운영하는 가장 확실한 방법입니다.
