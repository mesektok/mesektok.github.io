## 은퇴 후 시작한 블로그 여정, 그리고 그 첫 번째 난관

저는 대학에서 40년간 컴퓨터공학을 가르친 후 지난해 정년퇴직했습니다. 은퇴 후 시간이 많아지자 그동안 못했던 일들을 시작했는데, 그 중 하나가 바로 기술 블로그 운영이었습니다. 마크다운으로 글을 쓰고 GitHub에 올리면 자동으로 웹사이트가 생성되는 Jekyll과 GitHub Pages의 개념이 매력적으로 느껴졌거든요.

하지만 현실은 녹록지 않았습니다. 처음 세팅을 마치고 GitHub에 푸시했을 때, 빌드가 실패했다는 알림만 반복되었습니다. "Build failed"라는 짧은 메시지만 남겨질 뿐, 무엇이 잘못되었는지 알 수 없었습니다. 지금 생각해보니 그것이 제 블로깅 여정의 가장 답답했던 시간이었던 것 같습니다. 컴퓨터 업계에 50년을 몸담은 제가 이 정도 문제를 못 풀다니 하는 자존심도 상했고요.

## 로컬 환경과 GitHub Pages 환경의 "미묘한 차이"를 마주하다

결국 저는 한 달에 걸쳐 이 문제를 파고들었습니다. 첫 번째 깨달음은 "로컬에서 잘 되는 게 GitHub Pages에서도 잘 되는 건 아니다"는 것이었습니다.

제 맥북에서는 `jekyll serve` 명령어로 로컬 서버를 띄우면 완벽하게 작동했습니다. 글도 잘 보이고, 테마도 제대로 적용되고, 이미지도 로드되었습니다. 그런데 같은 코드를 GitHub에 푸시하면 왜 자꾸 실패할까요?

그 답은 **Gemfile과 Ruby 버전 관리**에 있었습니다. 저는 로컬에서 Ruby 3.3.0을 사용하고 있었는데, GitHub Pages가 지원하는 버전은 다를 수 있다는 것을 몰랐습니다. 더 정확히 말하면, GitHub Pages는 특정 Jekyll 플러그인만 화이트리스트에 등록해두고, 다른 gem들은 설치하지 않는다는 뜻입니다.

제가 사용한 일부 커스텀 플러그인들이 GitHub Pages의 안전 정책(safe mode)과 충돌하고 있었던 것입니다. 또한 `Gemfile.lock` 파일의 의존성 버전이 로컬과 원격에서 다르게 해석되고 있었습니다.

## 해결책: 명시적 설정과 GitHub Actions의 활용

제가 찾아낸 첫 번째 해결책은 간단했습니다. **Gemfile을 명확하게 작성하는 것**입니다. 저는 다음과 같이 수정했습니다:

```ruby
source "https://rubygems.org"

git_source(:github) { |repo| "https://github.com/#{repo}.git" }

gem "jekyll", "~> 4.3.0"
gem "minima", "~> 2.5"
gem "jekyll-feed", "~> 0.17"
gem "jekyll-seo-tag", "~> 2.8"
gem "webrick", "~> 1.7"

group :jekyll_plugins do
  gem "jekyll-feed"
  gem "jekyll-seo-tag"
end
```

특히 **webrick** gem을 명시적으로 추가한 것이 중요했습니다. Ruby 3.0 이상에서는 webrick이 기본 포함되지 않기 때문입니다.

그러나 더 근본적인 해결책은 **GitHub Actions를 이용한 자동 빌드**였습니다. GitHub Pages의 기본 Jekyll 빌드에만 의존하지 않고, 별도의 워크플로우를 구성하는 방식입니다. 저는 `.github/workflows/jekyll.yml` 파일을 다음과 같이 작성했습니다:

```yaml
name: Build and Deploy

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Ruby
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '3.1'
          bundler-cache: true
      - name: Build
        run: bundle exec jekyll build
      - name: Deploy
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./_site
```

이렇게 하면 로컬과 정확히 같은 환경에서 빌드가 진행되며, 빌드 실패 시에는 상세한 에러 로그까지 확인할 수 있습니다.

## 67세 교수가 깨달은 것: 명확성과 일관성의 중요성

이 문제를 해결하면서 저는 한 가지 중요한 깨달음을 얻었습니다. 기술은 결국 **명확한 설정과 일관성**을 요구한다는 것입니다. 로컬 개발 환경과 배포 환경이 다르다면, 그 차이를 명시적으로 관리해야 합니다.

제 학생들에게도 항상 강조했던 것인데, 은퇴 후에야 몸으로 깨닫게 되었습니다. 문서를 제대로 읽기, 에러 로그를 꼼꼼히 분석하기, 그리고 작은 변화부터 하나씩 테스트하기 — 이 기본적인 원칙들이 모
